

# TikTok 商家内容运营工作台文档生成 Skill

> 本 Skill 用于规范「TikTok Shop 商家内容运营工作台」项目中的所有产品、API、运营、合规和开发文档生成。  
> 目标不是把文档写长，而是让每份文档都边界清楚、阶段完整、能服务开发、能服务 TikTok API 审核。

---

## 0. 使用时机

当用户要求生成、修改、重写、补充本项目相关文档时，必须先套用本 Skill。

适用场景包括：

- 新建项目总文档
- 重写 00/01/02/03 等规划文档
- 生成产品设计文档
- 生成 API 申请文档
- 生成模块设计文档
- 生成 Codex 开发指令
- 生成阶段路线图
- 生成运营流程文档
- 修复“文档太乱、只写第一阶段、后续没讲清楚”的问题

不适用场景：

- 临时聊天解释
- 简单问答
- 单个术语解释
- 不需要进入项目文档体系的零散分析

## 1. 核心原则

### 1.1 第一原则：文档必须服务决策

每份文档开头必须回答：

```text
这份文档解决什么决策问题？
谁会使用这份文档？
它指导产品、API、开发、运营中的哪一类动作？
```

如果回答不出来，就不能生成这份文档。

### 1.2 第二原则：每份文档只解决一个主问题

禁止把以下内容混在同一份文档里：

- 产品定位
- 阶段路线图
- API 申请材料
- 页面字段设计
- 数据库模型
- Codex 开发任务
- 运营 SOP
- 合规规则
- 对外申请话术

可以在文档中引用其他内容，但不能把其他文档该承担的细节塞进来。

### 1.3 第三原则：任何文档都必须覆盖全阶段演进

每份文档不能只写“第一阶段怎么做”。

必须至少包含：

```text
当前阶段做什么
下一阶段怎么升级
后续阶段怎么演进
每个阶段的触发条件
每个阶段不能提前做什么
每个阶段和 API 申请的关系
```

### 1.4 第四原则：当前落地和长期蓝图必须分开

必须区分：

| 类型 | 含义 |
|---|---|
| 当前必须做 | 现在就能开发、能验证、能产生业务价值 |
| 当前只预留 | 当前不实现，但架构上要留接口 |
| 后续依赖 API | API 通过后才能做 |
| 后续依赖业务成熟 | 内部流程稳定后才能做 |
| 禁止作为主线 | 高风险、低确定性、容易误导审核的方向 |

### 1.5 第五原则：所有正式文档必须服务 API 审核形象

本项目所有正式文档必须把产品描述为：

```text
TikTok Shop 商家内容运营工作台
```

禁止把产品描述为：

```text
矩阵号工具
养号工具
自动群发工具
批量铺量工具
自动绕过上传工具
规避风控工具
无人值守发帖机器人
```

## 2. 文档体系总结构

本项目文档必须按以下体系拆分，不允许所有内容塞进 01 文档。

| 编号 | 文档名称 | 主问题 | 禁止写入 |
|---|---|---|---|
| 00 | 总纲与阶段路线图 | 最终系统是什么，V0-V6 怎么演进 | 具体页面字段、数据库细节 |
| 01 | 产品定位与边界 | 产品是什么、不是什​​么、服务谁 | API 材料细节、开发任务 |
| 02 | 系统总览与模块边界 | 有哪些模块、页面、数据流、角色关系 | 具体代码实现 |
| 03 | API 申请路线与审核材料 | 申请哪些 API、每个 API 需要什么材料 | 产品全量页面细节 |
| 04 | 发布工作台产品设计 | 视频任务、发布确认、内容日历怎么设计 | Shop 商品全流程 |
| 05 | 商品与挂车模块设计 | 商品池、SKU 匹配、挂车策略 | 发帖 API 审核材料全集 |
| 06 | 合规与审核机制 | 内容、商品、发布合规怎么检查 | 具体 UI 视觉设计 |
| 07 | 数据复盘与指标体系 | 播放、互动、成交、转化怎么复盘 | API 申请话术 |
| 08 | 开发阶段拆解与 Codex 指令 | 每阶段如何交给 Codex 开发 | 高层战略讨论 |
| 09 | 第三方平台与浏览器辅助方案 | SocialEcho、Metricool、OpenClaw 等怎么作为分支 | 作为主路线替代官方 API |
| 10 | 运营 SOP 与团队协作 | 运营每天怎么用系统 | API 权限申请细节 |

## 3. 文档类型判断规则

生成任何文档前，必须先判断文档类型。

### 3.1 总纲型文档

用于回答：

```text
这个项目最终要做成什么？
从 V0 到 V6 每个阶段是什么？
每个阶段为什么这么排？
```

典型文件：

```text
00_总纲与阶段路线图.md
```

必须包含：

- 最终产品形态
- 总体架构图
- V0-V6 阶段表
- 每阶段目标
- 每阶段交付物
- 每阶段 API 依赖
- 每阶段风险
- 每阶段进入下一阶段的条件

禁止包含：

- 页面字段全集
- 数据库表结构全集
- 具体接口代码
- 长篇 API 申请话术

### 3.2 产品定位型文档

用于回答：

```text
产品是什么？
不是什​​么？
服务谁？
解决什么问题？
对外怎么描述？
哪些表述不能出现？
```

典型文件：

```text
01_产品定位与边界.md
```

必须包含：

- 一句话定位
- 目标用户
- 核心场景
- 产品边界
- 对内定位
- 对外/API 审核定位
- 禁止话术
- 与后续阶段的关系

禁止包含：

- 具体页面字段全集
- API 申请材料全集
- Codex 开发指令
- 数据库模型

### 3.3 系统总览型文档

用于回答：

```text
系统由哪些模块组成？
模块之间怎么流转？
角色如何参与？
数据如何流动？
```

典型文件：

```text
02_系统总览与模块边界.md
```

必须包含：

- 模块总览
- 页面清单
- 角色关系
- 数据流
- 状态流
- 发布方式可插拔设计
- API 预留层

禁止包含：

- 某个页面的全部字段细节
- API 申请话术全文
- 具体开发任务拆解

### 3.4 API 审核型文档

用于回答：

```text
要申请哪些 TikTok API？
每个 API 为什么需要？
需要什么产品页面证明？
需要什么材料？
当前能申请到什么程度？
```

典型文件：

```text
03_API申请路线与审核材料.md
```

必须包含：

- API 能力地图
- Developer App/OAuth/Content Posting/Direct Post/TikTok Shop/Shoppable Video 分层
- 每个权限的用途
- 每个权限对应的产品页面
- 每个权限的申请材料
- 审核风险
- 不应出现的表达
- 失败后的替代路径

禁止包含：

- 全量产品设计
- 运营 SOP
- 数据库模型

### 3.5 模块设计型文档

用于回答：

```text
某个模块具体怎么用？
有哪些页面？
有哪些字段？
有哪些状态？
和其他模块怎么关联？
未来怎么升级？
```

典型文件：

```text
04_发布工作台产品设计.md
05_商品与挂车模块设计.md
06_合规与审核机制.md
07_数据复盘与指标体系.md
```

必须包含：

- 模块目标
- 用户角色
- 页面结构
- 核心字段
- 状态机
- 操作流程
- 与其他模块的关系
- API 依赖
- 阶段演进

禁止包含：

- 项目总纲
- 无关模块细节
- 过度开发任务拆解

### 3.6 开发任务型文档

用于回答：

```text
Codex 下一步应该改哪些文件？
实现哪些页面、接口、数据模型、测试？
验收标准是什么？
```

典型文件：

```text
08_开发阶段拆解与 Codex 指令.md
```

必须包含：

- 开发目标
- 任务编号
- 影响文件
- 数据模型
- 页面/接口要求
- 测试要求
- 验收标准
- 不做事项

禁止包含：

- 大段战略分析
- API 申请话术
- 空泛产品愿景

## 4. 阶段体系固定规则

本项目阶段必须统一使用 V0-V6，不允许每份文档自己发明阶段名。

| 阶段 | 名称 | 核心目标 | API 依赖 |
|---|---|---|---|
| V0 | 内部发布任务系统 | 不依赖 TikTok API，跑通人工上传闭环 | 无 |
| V1 | 商家内容工作台 MVP | 做出可审核的产品形态 | 无/弱依赖 |
| V2 | TikTok OAuth 授权 | 账号授权、解绑、权限说明 | TikTok Developer App/OAuth |
| V3 | Content Posting 测试 | 上传/私密发布/状态记录 | Content Posting API |
| V4 | Direct Post 审核 | 公开视频授权发布 | video.publish + audit |
| V5 | TikTok Shop 商品能力 | 商品、库存、价格、店铺状态同步 | TikTok Shop API |
| V6 | Shoppable Video / Product Anchor | 商品锚点、挂车自动化、成交复盘 | Shop/Creator/Affiliate 高级能力 |

每份文档出现阶段规划时，必须引用这套 V0-V6。

禁止使用含糊表达：

```text
后面再说
未来可以做
后续接 API
以后自动化
```

必须改成：

```text
该能力放在 V4，触发条件是 Direct Post audit 通过。
该能力放在 V5，触发条件是 TikTok Shop 商品 API 可用。
该能力放在 V6，触发条件是 Shoppable Video/Product Anchor 权限可用。
```

## 5. 每份文档必须有的固定章节

除非用户明确要求短文档，否则项目正式文档必须包含以下章节。

```markdown
# 文档标题

## 1. 文档目标
- 本文档解决什么问题
- 谁使用本文档
- 本文档不解决什么问题

## 2. 当前结论
- 当前阶段应该做什么
- 不应该做什么
- 最关键判断

## 3. 项目阶段位置
- 本文档对应 V0-V6 哪些阶段
- 当前阶段落地范围
- 后续阶段演进范围

## 4. 核心设计
- 根据文档类型写对应主体内容

## 5. 阶段演进
- V0 怎么做
- V1 怎么做
- V2 怎么做
- V3 怎么做
- V4 怎么做
- V5 怎么做
- V6 怎么做

## 6. API 审核关系
- 本文档内容如何服务 API 申请
- 哪些页面/流程/字段可以作为审核材料
- 哪些表述必须避免

## 7. 当前不做事项
- 明确列出不做什么
- 为什么不做
- 未来什么条件下再做

## 8. 验收标准
- 文档层面的验收标准
- 产品层面的验收标准
- 开发层面的验收标准，若适用
```

## 6. 写作风格规则

### 6.1 必须具体

不要写：

```text
后续优化发布能力。
```

要写：

```text
V4 阶段在 Direct Post audit 通过后，将发布方式从 manual/third_party 扩展为 tiktok_content_posting_api，并在发布记录中保存 publish_id、status、error_code、video_url。
```

### 6.2 必须能指导开发

不要写：

```text
系统支持商品管理。
```

要写：

```text
商品池至少包含：商品名称、SKU、TikTok Shop 商品 ID、商品图片、类目、核心卖点、价格、库存、可售状态、合规状态、适合视频场景。
```

### 6.3 必须明确边界

不要写：

```text
后续支持自动挂车。
```

要写：

```text
自动商品锚点能力放在 V6，不进入 V0-V3 主线。V0-V3 只做商品匹配建议、挂车操作指引和人工确认。
```

### 6.4 必须避免 AI 味废话

禁止高频出现以下空泛词：

```text
赋能
闭环生态
全链路智能化
高效协同
智能驱动
多维度提升
打造一体化平台
```

可以写，但必须落到字段、页面、状态、流程、验收标准。

### 6.5 可以狠，但必须可执行

允许指出错误方向，例如：

```text
如果第一版做成“一键批量群发”，会削弱 TikTok API 审核可信度。
```

但必须给出替代方案：

```text
第一版应设计为“批量准备，逐条审核，单条确认发布”。
```

## 8. 文档生成前检查清单

生成文档前，必须先在内部确认以下问题。

```text
1. 这份文档属于哪一类？
2. 它应该放在 00-10 哪个编号？
3. 它只解决一个主问题吗？
4. 它是否误把其他文档的内容塞进来了？
5. 它是否覆盖 V0-V6？
6. 它是否明确当前阶段和后续阶段的边界？
7. 它是否说明了 API 审核关系？
8. 它是否列出了当前不做事项？
9. 它是否能指导 Codex 或运营执行？
10. 它是否包含了不该出现在正式文档里的高风险表达？
```

如果第 3、5、6、7、8 任意一项不满足，不能输出正式文档。

## 9. 文档生成后自检清单

生成完成后，必须检查：

| 检查项 | 通过标准 |
|---|---|
| 边界清楚 | 没有把 3 份文档内容混在一起 |
| 阶段完整 | V0-V6 都有交代，至少说明哪些阶段相关 |
| 当前可落地 | 当前阶段能直接指导下一步动作 |
| 后续可衔接 | API 通过后怎么升级写清楚 |
| 审核友好 | 没有矩阵号/养号/规避风控等表达 |
| 可开发 | 至少包含页面、字段、状态、流程或验收标准之一 |
| 可裁剪 | 若文档太长，能拆到对应编号文档中 |

如果发现文档过杂，必须主动拆分，而不是继续堆内容。

## 10. 标准输出格式

当用户要求“生成文档”时，输出应遵循：

```text
1. 先说明将生成哪个编号文档
2. 说明该文档只解决什么问题
3. 直接写入或生成文档内容
4. 最后指出下一份最应该生成的文档
```

当用户要求“重写文档”时，输出应遵循：

```text
1. 先判断原文档哪里越界
2. 决定是重写还是拆分
3. 保留该文档主问题相关内容
4. 把越界内容迁移到对应文档建议中
5. 输出新版文档
```

当用户要求“补充后续阶段”时，输出应遵循：

```text
1. 不重写全文
2. 只补阶段演进章节
3. 必须按 V0-V6 写
4. 每阶段包含目标、能力、API 依赖、交付物、风险
```

## 11. 常见错误与修正

### 错误 1：01 文档写成大杂烩

错误表现：

```text
01 里同时写产品定位、API 申请、页面字段、MVP、里程碑、申请话术。
```

修正：

```text
01 只保留产品定位、边界、用户、对外表达、禁止表达。
阶段路线迁移到 00。
API 申请迁移到 03。
页面字段迁移到 04/05。
开发任务迁移到 08。
```

### 错误 2：只写第一阶段

错误表现：

```text
V0 写了 3000 字，V1-V6 只写“后续扩展”。
```

修正：

```text
每个阶段必须写：目标、能力、触发条件、交付物、API 依赖、当前是否实现。
```

### 错误 3：把不能做的能力写成近期目标

错误表现：

```text
第一阶段实现自动公开视频发布和自动挂车。
```

修正：

```text
V0-V1 只做人工发布和发布确认页。
V3 才做 Content Posting 测试。
V4 才做 Direct Post。
V6 才考虑商品锚点自动化。
```

### 错误 4：文档无法指导 Codex

错误表现：

```text
写了很多愿景，没有页面、字段、状态、验收标准。
```

修正：

```text
模块设计文档必须包含页面结构、字段清单、状态机、操作流程、验收标准。
开发文档必须包含任务编号、影响文件、接口、测试要求。
```

### 错误 5：对外表达像灰产工具

错误表现：


## 13. 质量标准

一份合格文档必须满足：

```text
有主问题
有边界
有阶段
有当前落地
有后续演进
有 API 审核关系
有不做事项
有验收标准
没有高风险表达
没有把多个文档混成一锅粥
```

一份不合格文档的典型表现：

```text
标题是产品定位，内容却写了 API、页面、开发、运营、申请话术；
只写 V0，不写 V1-V6；
后续阶段全是“未来扩展”；
没有说明什么条件触发下一阶段；
看完后 Codex 不知道该开发什么；
看完后 API 审核材料也不能直接复用。
```

## 14. 最终铁律

```text
先定文档类型，再定文档边界；
```
