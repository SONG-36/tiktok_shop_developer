

# 01_产品定位与边界

> 本文档用于定义「TikTok Shop 商家内容运营工作台」的产品定位、目标用户、核心场景、产品边界和对外表达。  
> 本文档只解决“产品是什么、不是什​​么、服务谁、边界在哪里、对外怎么说”这一个主问题。  
> 阶段路线见 `00_总纲与阶段路线图.md`；API 申请材料见 `03_API申请路线与审核材料.md`；页面字段设计见 `04_发布工作台产品设计.md` 和 `05_商品与挂车模块设计.md`。

## 2. 当前结论

### 2.1 产品一句话定位

本产品是：

```text
面向 TikTok Shop 商家和品牌团队的内容运营工作台，帮助商家管理短视频素材、商品匹配、合规审核、授权发布和发布后数据复盘。
```

英文定位：

```text
A content operation workspace for TikTok Shop merchants and brand teams, helping merchants manage short-form video assets, product matching, compliance review, authorized publishing, and post-performance tracking.
```

### 2.2 产品不是什​​么

本产品不是：

```text
自动批量发视频工具
矩阵号群发系统
养号工具
浏览器自动上传工具
规避风控工具
搬运视频工具
无人值守发布机器人
```

### 2.3 当前最关键判断

产品第一性原理不是“自动化发布”，而是：

```text
把 TikTok Shop 商家的内容运营流程标准化、产品化、可审核化。
```

如果没有商品池、视频任务、商品匹配、合规审核、发布确认、发布记录和数据复盘，单纯做“自动上传”没有长期价值，也不利于 TikTok API 审核。

## 3. 项目阶段位置

### 3.1 本文档覆盖哪些阶段

本文档覆盖 V0-V6 的产品定位，但不展开阶段路线细节。

| 阶段 | 产品定位重点 |
|---|---|
| V0 内部发布任务系统 | 证明系统能服务真实运营流程，不是空壳工具 |
| V1 商家内容工作台 MVP | 证明系统具备 SaaS 化、可审核的产品形态 |
| V2 TikTok OAuth 授权 | 证明用户主动授权账号，而不是后台盗用账号 |
| V3 Content Posting 测试 | 证明发布动作基于用户确认和官方流程 |
| V4 Direct Post 审核 | 证明公开视频发布符合用户控制和审核要求 |
| V5 TikTok Shop 商品能力 | 证明内容发布和真实商品、库存、价格绑定 |
| V6 Shoppable Video / Product Anchor | 证明商品锚点建立在内容、商品、合规和数据闭环之上 |

### 3.2 当前阶段定位

当前阶段定位为：

```text
内部发布任务系统 + 商家内容工作台 MVP 的准备阶段
```

也就是：

- 先把公司内部商品、视频、账号、发布、复盘流程标准化
- 同时让产品形态为未来 API 审核做准备
- 不把自动公开视频发布和自动挂车写成当前能力

## 4. 目标用户

### 4.1 一级目标用户：TikTok Shop 商家

这是本产品最核心的用户。

他们的问题是：

```text
商品多，视频多，账号多，运营多人协作；
不知道每条视频对应哪个商品；
不知道哪个视频该发到哪个账号；
不知道发布前有没有合规风险；
不知道挂车商品是否正确；
不知道发布后哪个视频真正带来成交。
```

本系统为他们提供：

| 能力 | 价值 |
|---|---|
| 商品池 | 把可推广商品沉淀为可用内容资产 |
| 视频任务 | 每条视频有商品、账号、负责人、发布时间 |
| 商品匹配 | 减少挂错商品、乱挂商品 |
| 合规审核 | 降低内容、商品、商业披露风险 |
| 发布确认 | 避免发错号、发错视频、发错商品 |
| 数据复盘 | 判断哪些内容、商品、账号有效 |

### 4.2 二级目标用户：品牌内容团队

品牌团队关注的是：

- 视频素材是否统一管理
- 内容是否符合品牌表达
- 商品卖点是否一致
- 多账号发布是否有节奏
- 发布后表现是否可复盘

本系统提供：

```text
素材管理
内容日历
品牌卖点管理
发布审核
发布记录
内容表现复盘
```

### 4.3 三级目标用户：内容运营团队

内容运营团队每天需要处理：

- 生成或上传视频
- 写标题和标签
- 选择发布账号
- 选择挂车商品
- 检查是否发布成功
- 回填播放和互动数据

本系统要让运营从“靠记忆和表格”变成“按任务流执行”。

### 4.4 暂不作为核心用户的人群

| 用户类型 | 为什么暂不作为核心用户 |
|---|---|
| 纯达人/个人创作者 | 本项目主线是 TikTok Shop 商家内容运营，不是个人创作工具 |
| MCN 矩阵号团队 | 容易把产品拉向批量群发和账号矩阵，不利于审核定位 |
| 纯广告投放团队 | 广告 API 和自然内容发布是不同产品线 |
| 纯 ERP 用户 | ERP 关注订单、库存、财务；本项目主线是内容运营 |
| 爬虫数据分析用户 | 需求挖掘和数据抓取不是本工作台第一主线 |

## 5. 核心业务问题

### 5.1 当前业务混乱点

本产品要解决的不是“怎么点发布按钮”，而是内容运营中的系统性混乱。

| 问题 | 典型表现 | 系统解决方式 |
|---|---|---|
| 商品和视频断裂 | 视频做好了，但不知道对应哪个 SKU | 视频任务必须绑定商品 |
| 发布任务不清楚 | 谁发、发哪条、发哪个号靠口头沟通 | 内容日历和任务负责人 |
| 标题标签不沉淀 | 每次临时写，无法复盘 | 标题标签生成和记录 |
| 挂车容易出错 | 商品不一致、库存不足、价格异常 | 商品匹配和发布前校验 |
| 审核靠感觉 | 违规词、夸大宣传、商业披露没人检查 | 合规审核机制 |
| 数据回不来 | 发完不知道哪个内容有效 | 发布记录和数据复盘 |
| API 申请没依据 | 系统看起来像内部批量上传脚本 | 商家工作台产品形态 |

### 5.2 产品要沉淀的核心资产

本系统要沉淀 5 类资产：

| 资产 | 说明 |
|---|---|
| 商品资产 | SKU、卖点、图片、库存、价格、合规状态 |
| 内容资产 | 视频、封面、脚本、标题、标签、素材来源 |
| 发布资产 | 账号、时间、发布方式、状态、链接、错误码 |
| 合规资产 | 检查结果、审核记录、驳回原因、商业披露 |
| 数据资产 | 播放、互动、点击、成交、转化、复盘结论 |

如果一个功能不能沉淀以上资产之一，就要谨慎判断是否应该进入主线。

## 6. 产品边界

### 6.1 当前必须做

| 能力 | 原因 |
|---|---|
| 商品池 | 内容运营必须围绕商品展开 |
| 视频任务 | 所有视频必须可追踪 |
| 内容日历 | 多账号、多商品发布需要排期 |
| 发布确认 | 为人工发布和未来 Direct Post 做准备 |
| 商品匹配建议 | 为挂车和商品一致性检查做准备 |
| 合规审核 | 为平台安全和 API 审核做准备 |
| 发布记录 | 为复盘和 API 调试做准备 |
| 数据回填 | 即使先人工，也要形成复盘闭环 |

### 6.2 当前只预留，不实现

| 能力 | 当前做法 | 未来阶段 |
|---|---|---|
| TikTok OAuth | 做授权中心入口和页面占位 | V2 |
| Content Posting | 发布方式中预留 `tiktok_content_posting_api` | V3/V4 |
| TikTok Shop API | 商品池预留 TikTok Shop 商品 ID 字段 | V5 |
| 商品锚点 API | 商品匹配结果预留 anchor 状态 | V6 |
| 第三方发布平台 | 发布方式预留 `third_party_platform` | 09 文档评估 |

### 6.3 当前不做

| 能力 | 不做原因 | 未来是否可能做 |
|---|---|---|
| 全自动公开视频发布 | 依赖 Direct Post audit，且审核敏感 | V4 通过后做 |
| 自动挂购物车 | 依赖更深的 Shop/Creator/Affiliate 权限 | V6 做 |
| 一键多账号批量群发 | 不利于 API 审核形象 | 不作为主线 |
| 养号标签系统 | 高风险表达和高风险业务 | 不进入正式产品 |
| 浏览器自动绕过发布 | 非官方主线，稳定性和合规风险高 | 仅作为实验分支 |
| 搬运视频管理 | 违背原创/商家内容运营定位 | 不做 |

## 7. 对内定位与对外定位

### 7.1 对内定位

对公司内部，可以这样理解：

```text
这是一个帮助运营团队管理 TikTok 视频发布任务的工作台。
它先解决商品、视频、账号、发布时间、挂车商品、发布状态和数据复盘的问题。
后续如果 TikTok API 申请通过，再把人工发布逐步升级为官方授权发布。
```

对内可以讨论效率和自动化，但必须记住：

```text
自动化是后续能力，不是第一阶段产品定位。
```

### 7.2 对外/API 审核定位

对 TikTok 官方、API 审核、官网、产品介绍，应使用：

```text
本产品是面向 TikTok Shop 商家和品牌团队的内容运营工作台，帮助商家管理短视频素材、商品 SKU 匹配、内容合规审核、授权发布和发布后数据复盘。
```

英文：

```text
Our product is a content operation workspace for TikTok Shop merchants and brand teams. It helps merchants manage short-form video assets, match videos with their shop products, review content compliance, configure publishing tasks, authorize TikTok account publishing, and track post-publishing performance.
```

### 7.3 官网/申请材料短描述

中文短描述：

```text
帮助 TikTok Shop 商家更安全、更高效地管理短视频内容、商品匹配、发布确认和数据复盘。
```

英文短描述：

```text
A workspace for TikTok Shop merchants to manage video content, product matching, publishing review, and performance tracking.
```

以下表达不能出现在官网、API 申请材料、产品介绍、对外演示中：

```text
矩阵号

规避风控
```

### 8.2 容易误导审核的表达

| 不推荐表达 | 替代表达 |
|---|---|
| 自动批量发布 TikTok 视频 | 商家授权发布和发布任务管理 |
| 多账号矩阵管理 | 多店铺/多账号内容排期管理 |
| 自动挂车卖货 | 商品匹配和商品锚点管理 |

### 8.3 内部也要少用的表达

即使内部讨论，也应减少使用：

```text
矩阵
养号
铺量
怼视频
批量薅流量
规避审核
```

原因不是装正经，而是这些词会把产品设计拉偏。

## 9. API 审核关系

### 9.1 为什么定位必须服务 API 审核

TikTok Content Posting API 的 Direct Post 能力要求 API client 通过 audit 后才可解除公开视频可见性限制；未审核 client 发布内容会被限制为 private viewing mode。  
因此，本产品不能从一开始就表现得像无人值守批量发布工具。

TikTok Developer App 还要求对外网站、隐私政策、服务条款等 URL 属性验证。  
因此，本产品必须具备真实产品形态，而不是临时内部脚本。

TikTok Shop API 主要服务商品目录、订单、物流、支付等 Seller Center 扩展能力。  
因此，本产品必须把“商品池、SKU、库存、价格、商品状态”作为内容运营的一部分，而不是只做视频发布。

### 9.2 产品定位如何支撑 API 申请

| API 能力 | 产品定位支撑 |
|---|---|
| OAuth / Login | 用户主动授权 TikTok 账号，用于商家内容发布管理 |
| Content Posting | 用户在工作台预览、编辑、确认后发布视频 |
| Direct Post | 商家授权并确认发布设置后，从工作台发布内容 |
| TikTok Shop API | 商家同步自己的商品、库存、价格，用于视频商品匹配 |
| Shoppable Video / Product Anchor | 在商品匹配、合规审核、发布确认成熟后管理商品锚点 |

### 9.3 定位上必须坚持的审核友好特征

```text
用户主动授权
发布前确认
标题可编辑
视频可预览
商品可确认
商业内容可披露
操作可追踪
账号可解绑
数据可删除
```

这些特征后续必须体现在 02、03、04、05 文档和产品页面里。

## 10. 当前不做事项

### 10.1 不做事项表

| 不做事项 | 为什么不做 | 未来触发条件 |
|---|---|---|
| 全自动公开视频发布 | 未通过 Direct Post audit 前不能作为确定能力 | V4 审核通过 |
| 自动挂购物车 | 需要 Shoppable Video/Product Anchor 相关能力 | V6 权限可用 |
| 浏览器自动控制 TikTok 发布 | 不作为官方 API 审核主线 | 仅 09 文档实验评估 |
| 多账号群发后台 | 容易变成矩阵号工具 | 不进入主线 |
| 账号养标签模块 | 高风险表达，不利于产品定位 | 不做正式模块 |
| 纯数据爬虫选品系统 | 与本工作台主线不同 | 可另立项目 |
| ERP 全功能系统 | 本项目主线是内容运营，不是订单财务 ERP | V5 后按需对接 |

### 10.2 判断一个新功能是否该做

新增功能必须先问 5 个问题：

```text
1. 它是否服务 TikTok Shop 商家的内容运营？
2. 它是否沉淀商品、内容、发布、合规或数据资产？
3. 它是否有助于 API 审核形象？
4. 它是否会让产品看起来像矩阵号/群发/养号工具？
5. 它应该放在 V0-V6 哪个阶段？
```

如果第 4 个问题答案是“是”，该功能不能进入正式主线。


后续开发任务必须符合：

```text
功能名称不能使用矩阵、养号、铺量、规避风控等表达；
发布相关字段必须包含发布方式、发布状态、操作者、发布时间、视频链接或错误原因；
商品相关字段必须为未来 TikTok Shop 商品 ID、SKU、库存、价格状态预留空间；
发布方式必须可插拔，不能只写死人工或 API。
```

## 12. 当前版本结论

本产品的正确定位是：

```text
TikTok Shop 商家内容运营工作台
```

不是：

```text
TikTok 自动发视频工具
```

当前要先建立：

```text
商品池
视频任务
内容日历
商品匹配
合规审核
发布确认
发布记录
数据复盘
```

后续再按 V0-V6 路线逐步接入：

```text
TikTok OAuth
Content Posting API
Direct Post
TikTok Shop API
Shoppable Video / Product Anchor
```

如果产品定位从第一天就写成“自动批量发布”，后面 API 申请、产品设计、团队执行都会跑偏。

所以本项目必须坚持一句话：

```text
先做商家内容运营工作台，再做官方授权自动化。
```
