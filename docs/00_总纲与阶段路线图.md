

# 00_总纲与阶段路线图

> 本文档是「TikTok Shop 商家内容运营工作台」项目的总纲。  
> 它只回答一个问题：系统最终要做成什么，以及从 V0 到 V6 应该如何一步步演进。  
> 本文档不展开具体页面字段、不写数据库模型、不写 Codex 任务细节；这些内容分别放到 02、04、05、08 等后续文档中。

## 1. 文档目标

### 1.1 本文档解决什么问题

本文档解决项目最容易混乱的三个问题：

1. **最终系统到底是什么**  
   防止项目被误写成“自动发视频工具”“矩阵号工具”“养号工具”。

2. **阶段路线怎么走**  
   防止每次只写 V0/V1，后续 Direct Post、TikTok Shop API、Shoppable Video 等能力变成一句“未来扩展”。

3. **每个阶段为什么这么排**  
   防止把当前拿不到、风险高、依赖 API 审核的能力提前写成第一阶段目标。

| 使用者 | 用法 |

## 2. 当前结论

### 2.1 最终产品形态

本项目最终要做成：

```text
TikTok Shop 商家内容运营工作台
```

它面向 TikTok Shop 商家、品牌团队和内容运营团队，帮助他们完成：

```text
商品池管理
  ↓
视频任务创建
  ↓
素材管理 / AI 视频生成
  ↓
标题、标签、卖点生成
  ↓
商品 SKU 匹配
  ↓
内容与商品合规检查
  ↓
人工审核 / 发布确认
  ↓
人工发布 / 第三方发布 / TikTok API 发布
  ↓
商品挂车 / 商品锚点
  ↓
发布状态追踪
  ↓
播放、互动、成交数据复盘
```

### 2.2 当前阶段最应该做什么

当前最应该做的是：

```text
V0：内部发布任务系统
```

也就是先不依赖 TikTok API，把公司内部的内容发布流程跑顺：

- 商品池
- 视频任务
- 内容日历
- 发布确认
- 人工上传 checklist
- 发布记录
- 数据回填

### 2.3 当前阶段不应该做什么

当前阶段不要把以下能力作为主线：

| 能力 | 为什么现在不做 | 放到哪个阶段 |
|---|---|---|
| 自动公开视频发布 | 依赖 Content Posting API、video.publish scope 和 Direct Post audit | V4 |
| 自动挂购物车/商品锚点 | 属于更深的 TikTok Shop / Shoppable Video / Product Anchor 能力 | V6 |
| 浏览器自动化全自动上传 | 非官方主线，稳定性和合规风险高 | 09 文档单独评估 |
| 多账号批量群发 | 容易破坏 API 审核形象 | 不作为主线 |
| 账号养标签 | 高风险表达，不进入正式文档 | 不作为正式能力 |

### 2.4 最关键判断

本项目的核心不是“让电脑自动点发布按钮”。

真正核心是：

```text
把 TikTok Shop 商家的内容运营流程标准化、产品化、可审核化。
```

只有先做到这一点，后续申请 TikTok OAuth、Content Posting API、Direct Post、TikTok Shop API、Shoppable Video API 才有合理产品依据。

## 3. 项目阶段位置

### 3.1 固定阶段体系

本项目统一使用 V0-V6 阶段体系。

| 阶段 | 名称 | 核心目标 | API 依赖 | 当前状态 |
|---|---|---|---|---|
| V0 | 内部发布任务系统 | 不依赖 TikTok API，跑通人工上传闭环 | 无 | 当前主线 |
| V1 | 商家内容工作台 MVP | 做出可审核的产品形态 | 无/弱依赖 | 下一阶段 |
| V2 | TikTok OAuth 授权 | 账号授权、解绑、权限说明 | TikTok Developer App/OAuth | 后续 |
| V3 | Content Posting 测试 | 上传/私密发布/状态记录 | Content Posting API | 后续 |
| V4 | Direct Post 审核 | 公开视频授权发布 | video.publish + audit | 后续 |
| V5 | TikTok Shop 商品能力 | 商品、库存、价格、店铺状态同步 | TikTok Shop API | 后续 |
| V6 | Shoppable Video / Product Anchor | 商品锚点、挂车自动化、成交复盘 | Shop/Creator/Affiliate 高级能力 | 后续 |

### 3.2 为什么必须这样分阶段

TikTok Content Posting API 的 Direct Post 能力不是普通开发者注册后就能随便公开视频发布。官方说明未审核 client 发布内容会被限制为 private viewing mode，解除可见性限制需要 API client 完成 audit。  
因此，V0/V1 不能把“自动公开视频发布”当作已确定能力。

TikTok Shop API 的主要能力覆盖 catalogs、orders、shipments、payments 等商家数据域，用于扩展 Seller Center 的功能。  
因此，商品同步、库存价格校验放在 V5 更合理。

Shoppable Video / Product Anchor 相关能力属于更深的内容商品化能力。  
因此，自动挂购物车不进入 V0-V3 主线，而放在 V6。

## 4. 最终系统总览

### 4.1 系统最终形态

最终系统不是一个单点工具，而是一套商家内容运营工作台。

```text
┌────────────────────────────────────┐
│        TikTok Shop 商家内容运营工作台        │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  1. 商品池：SKU、卖点、库存、合规、平台状态  │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  2. 视频任务：脚本、素材、账号、发布时间、状态 │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  3. 内容生产：AI 视频、实拍素材、封面、标题标签 │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  4. 商品匹配：视频内容 ↔ SKU ↔ 挂车建议       │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  5. 合规审核：内容、商品、商业披露、发布设置    │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  6. 发布确认：账号、视频、标题、隐私、商品确认   │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  7. 发布执行：人工 / 第三方平台 / TikTok API    │
└────────────────────────────────────┘
                 │
                 ▼
┌────────────────────────────────────┐
│  8. 数据复盘：播放、互动、点击、成交、ROI       │
└────────────────────────────────────┘
```

### 4.2 系统核心模块

| 模块 | 作用 | 主要阶段 |
|---|---|---|
| 商品池 | 管理商品资料、SKU、卖点、库存、平台状态 | V0-V5 |
| 素材库 | 管理 AI 视频、实拍素材、封面、参考素材 | V0-V1 |
| 视频任务 | 管理每条视频从创建到发布的状态 | V0-V6 |
| 内容日历 | 管理不同账号、日期、时间的发布排期 | V0-V6 |
| 发布确认页 | 发布前确认账号、视频、标题、商品、隐私、商业内容 | V0-V4 |
| 合规检查 | 检查内容、商品、挂车、商业披露风险 | V0-V6 |
| API 授权中心 | 管理 TikTok OAuth、Shop 授权、权限状态 | V2-V6 |
| 发布执行器 | 支持 manual、third_party、tiktok_content_api 等方式 | V0-V6 |
| 发布记录 | 保存发布状态、链接、错误码、操作者 | V0-V6 |
| 数据复盘 | 统计播放、互动、点击、成交、转化 | V0-V6 |

### 4.3 发布方式必须可插拔

系统不能绑定单一发布方式。

统一抽象为：

```text
publisher_type:
  - manual
  - assisted_browser
  - third_party_platform
  - tiktok_content_posting_api
  - tiktok_shop_shoppable_api
```

| 发布方式 | 所属阶段 | 说明 |
|---|---|---|
| manual | V0 起 | 运营人工上传，系统提供任务、素材、标题、标签、挂车指引 |
| assisted_browser | 实验分支 | 浏览器辅助预填，不作为 API 审核主线 |
| third_party_platform | V1/V2 起可评估 | 接 SocialEcho、Metricool、Later、Buffer 等平台 |
| tiktok_content_posting_api | V3/V4 | Content Posting API 上传或 Direct Post 发布 |
| tiktok_shop_shoppable_api | V6 | Shoppable Video / Product Anchor 能力成熟后接入 |

## 5. V0-V6 阶段演进

## 5.1 V0：内部发布任务系统

### 阶段目标

不依赖 TikTok API，先把内部“视频生产 → 商品匹配 → 发布安排 → 人工上传 → 数据回填”的流程跑通。

### 为什么先做 V0

如果内部流程都没有标准化，直接做 API 申请和自动发布就是空中楼阁。

V0 要解决的是：

```text
谁负责哪个商品？
哪个商品要发哪些视频？
哪个视频发到哪个账号？
什么时候发？
标题标签是什么？
挂哪个商品？
发布了吗？
发布后效果怎么样？
```

### 核心能力

| 能力 | 说明 |
|---|---|
| 商品池 | 建立可用于内容生产的商品资料 |
| 视频任务 | 每条视频都有任务、商品、账号、负责人、状态 |
| 内容日历 | 按账号和日期安排发布 |
| 标题标签生成 | AI 辅助生成，人工确认 |
| 商品匹配建议 | 系统推荐 SKU，人工确认 |
| 发布确认页静态版 | 不接 API，但先按 API 审核需要设计页面形态 |
| 人工上传 checklist | 运营按 checklist 到 TikTok 手动上传 |
| 发布记录 | 手动回填视频链接、发布时间、状态 |
| 数据回填 | 手动记录播放、点赞、评论、成交等基础数据 |

### 交付物

```text
商品池
视频任务表
内容日历
发布确认页静态版
发布记录
人工上传 checklist
基础数据回填表
```

### API 依赖

无。

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| TikTok OAuth | V0 先跑通内部流程 | V2 |
| Content Posting | 需要 API 权限和测试 | V3 |
| Direct Post | 需要 audit | V4 |
| Shop 商品同步 | 需要 TikTok Shop API | V5 |
| 自动挂车 | 需要更深权限 | V6 |

### 进入 V1 的条件

- 商品池能支撑真实视频任务
- 视频任务能跑完创建、审核、发布、回填流程
- 发布确认页静态版能表达账号、视频、标题、商品、合规、发布设置
- 运营能按照 checklist 实际上传视频
- 发布记录可用于复盘

## 5.2 V1：商家内容工作台 MVP

### 阶段目标

把 V0 的内部任务系统升级成一个“像真正 SaaS 产品”的商家内容工作台 MVP。

V1 的重点不是 API，而是产品形态。

### 为什么需要 V1

API 审核不是只看接口能力，也看应用是否真实、是否有合理用户场景、是否有授权和数据控制设计。

V1 要让系统具备对外可信形态：

```text
不是内部表格
不是临时脚本
不是批量发号工具
而是商家内容运营工作台
```

### 核心能力

| 能力 | 说明 |
|---|---|
| 用户登录 | 支持团队成员登录 |
| 店铺/团队管理 | 管理公司、店铺、成员、角色 |
| 角色权限 | 管理员、运营、审核人、发布人、数据分析 |
| 发布确认页正式 UX | 按未来 Direct Post 要求设计发布前确认体验 |
| 授权中心占位 | 预留 TikTok OAuth、Shop 授权入口 |
| 隐私政策/服务条款页面 | 为后续 App 审核准备 |
| 数据删除说明 | 为 OAuth 和数据合规准备 |
| 操作日志 | 记录谁创建、审核、发布、修改 |

### 交付物

```text
商家内容工作台 MVP
用户与角色系统
店铺/团队管理
发布确认页正式版
授权中心占位
隐私政策
服务条款
数据删除说明
操作日志
```

### API 依赖

无或弱依赖。

此阶段可以先不真正调用 TikTok API，但页面、流程、字段必须为 V2-V4 做准备。

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| 真正 OAuth 授权 | V1 先完成产品形态和入口 | V2 |
| 视频上传到 TikTok | 需要 Content Posting 权限 | V3 |
| 公开视频 Direct Post | 需要 audit | V4 |
| 商品 API 同步 | 需要 Shop API | V5 |

### 进入 V2 的条件

- 系统有真实登录入口
- 有账号授权中心入口
- 有隐私政策、服务条款、数据删除说明
- 有发布确认页完整 UX
- 有账号解绑/撤销授权的产品设计
- 能录制一段产品演示视频用于 API 审核准备

## 5.3 V2：TikTok OAuth 授权

### 阶段目标

实现 TikTok 账号授权、授权状态展示、账号解绑和权限说明。

### 为什么 V2 只做授权

不要一申请 API 就急着发视频。

TikTok API 申请的第一步应该是：

```text
用户能主动把自己的 TikTok 账号授权给系统；
系统能展示授权账号；
用户能解绑；
系统能解释为什么需要这些权限。
```

这是后续 Content Posting 和 Direct Post 的基础。

### 核心能力

| 能力 | 说明 |
|---|---|
| TikTok Developer App | 创建开发者应用 |
| OAuth 登录/授权 | 用户主动授权 TikTok 账号 |
| 授权账号列表 | 展示头像、昵称、账号状态、授权时间 |
| 权限说明 | 展示每个 scope 的用途 |
| 账号解绑 | 用户可撤销授权 |
| 数据删除流程 | 用户解绑后停止使用或删除相关数据 |
| 授权日志 | 记录授权、刷新、解绑事件 |

### 交付物

```text
TikTok OAuth 接入
授权中心
授权账号列表
解绑功能
scope 权限说明
数据删除说明
OAuth 审核录屏
```

### API 依赖

```text
TikTok Developer App
OAuth / Login Kit
基础用户信息权限
```

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| 视频上传 | V2 只处理授权 | V3 |
| Direct Post | 需要发布 API 和 audit | V4 |
| 商品同步 | 属于 TikTok Shop API | V5 |
| 自动挂车 | 属于更高阶能力 | V6 |

### 进入 V3 的条件

- TikTok 账号可以成功授权
- 授权账号可以展示在系统中
- 用户可以解绑账号
- 权限说明清楚
- 隐私政策、服务条款、数据删除说明可访问
- OAuth 审核材料可提交

## 5.4 V3：Content Posting 测试

### 阶段目标

跑通 Content Posting API 的上传/测试流程，并记录发布状态。

V3 的目标不是公开视频批量发布，而是：

```text
证明系统可以把用户确认过的视频，通过官方 Content Posting 流程提交给 TikTok，并记录结果。
```

### 为什么 V3 不直接做公开视频

官方明确说明，未审核 client 发布内容会被限制为 private viewing mode。  
因此 V3 应该把目标定为测试、上传、私密发布、状态记录，而不是公开视频自动发布。

### 核心能力

| 能力 | 说明 |
|---|---|
| 视频上传初始化 | 初始化上传/发布任务 |
| 视频文件传输 | 将视频传输到 TikTok |
| 发布请求记录 | 保存 publish_id、状态、错误信息 |
| 私密/测试发布 | 按未审核 client 限制进行测试 |
| 错误码记录 | 记录失败原因和错误码 |
| 发布状态查询 | 查询处理中、成功、失败状态 |
| 发布流程录屏 | 为 Direct Post audit 准备材料 |

### 交付物

```text
Content Posting API 测试接入
视频上传流程
发布状态记录
错误码记录
测试账号
测试视频
测试发布录屏
```

### API 依赖

```text
Content Posting API
video.upload / video.publish 相关权限，视申请结果而定
```

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| 公开视频发布 | 未审核 client 存在私密限制 | V4 |
| 批量无人发布 | 不符合审核友好形态 | 不作为主线 |
| 自动挂商品锚点 | 不是 Content Posting 基础目标 | V6 |

### 进入 V4 的条件

- Content Posting 测试流程稳定
- 发布确认页完整展示账号、视频、标题、隐私、互动设置、商业内容披露
- 发布状态和错误处理完整
- 已准备 Direct Post audit 所需截图、录屏、说明
- 系统能证明用户在发布前做出了明确确认

## 5.5 V4：Direct Post 审核

### 阶段目标

申请并通过 Direct Post audit，实现用户授权后的公开视频发布能力。

### 阶段本质

V4 是 API 审核阶段，不是单纯开发阶段。

系统必须向 TikTok 证明：

```text
用户主动授权账号；
用户能预览视频；
用户能编辑标题；
用户能配置发布设置；
用户能确认商业内容；
用户在发布前明确点击确认；
系统记录发布状态；
用户能解绑账号和删除数据。
```

### 核心能力

| 能力 | 说明 |
|---|---|
| Direct Post 发布 | 用户确认后从系统发布到 TikTok |
| creator info 渲染 | 根据 TikTok 返回的创作者信息展示可用发布设置 |
| 隐私设置 | 按账号能力展示公开/好友/私密等设置 |
| 评论/合拍/拼接设置 | 保留创作者控制权 |
| 商业内容披露 | 电商视频必须重点处理 |
| 发布前确认 | 不能后台静默发布 |
| 发布状态追踪 | 记录成功、失败、处理中 |
| 审核材料包 | 截图、录屏、权限说明、合规说明 |

### 交付物

```text
Direct Post 发布流程
发布确认页审核版
发布设置渲染
商业内容披露
发布日志
错误处理
Direct Post audit 材料包
```

### API 依赖

```text
Content Posting API
video.publish scope
Direct Post audit 通过
```

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| 商品 API 自动同步 | 属于 Shop 能力 | V5 |
| 自动商品锚点 | 属于 Shoppable Video / Product Anchor | V6 |
| 高并发批量发布 | 审核和风控风险高 | 不作为主线 |

### 进入 V5 的条件

- Direct Post audit 通过
- 公开视频发布稳定
- 发布日志和错误处理稳定
- 商业内容披露流程清楚
- 系统不再依赖人工复制标题和视频链接作为主要发布方式

## 5.6 V5：TikTok Shop 商品能力

### 阶段目标

接入 TikTok Shop API，同步商品、库存、价格、店铺状态，为商品匹配和挂车准备提供真实数据。

### 为什么 V5 在 Direct Post 后

商品能力虽然可以独立申请，但对本项目来说，只有在发布工作台基本成型后，Shop API 才能发挥更大价值。

V5 解决的是：

```text
视频到底该挂哪个商品？
商品是否可售？
库存是否足够？
价格是否异常？
商品状态是否适合发布？
```

### 核心能力

| 能力 | 说明 |
|---|---|
| Shop 授权 | 商家授权 TikTok Shop 数据 |
| 商品同步 | 同步商品 ID、标题、图片、SKU、类目 |
| 库存同步 | 获取库存状态和库存阈值 |
| 价格同步 | 获取商品价格、促销价、异常价格 |
| 商品状态 | 上架、下架、审核中、不可售 |
| 商品匹配增强 | 根据真实商品数据推荐 SKU |
| 发布前商品校验 | 商品不可售时阻断或提醒 |

### 交付物

```text
TikTok Shop 授权
商品同步
库存同步
价格同步
商品状态检查
商品匹配增强
发布前商品校验
```

### API 依赖

```text
TikTok Shop API
Product API
Order API，若进入成交复盘
Finance API，若进入财务复盘
```

### 当前不做

| 不做事项 | 原因 | 后续阶段 |
|---|---|---|
| 自动商品锚点 | 仍需 Shoppable Video/Product Anchor 权限 | V6 |
| 自动成交归因 | 需要数据口径稳定 | V6/后续 |
| ERP 深度双向同步 | 先验证 TikTok Shop 数据闭环 | 后续扩展 |

### 进入 V6 的条件

- 商品、库存、价格同步稳定
- 视频任务能稳定绑定 TikTok Shop 商品 ID/SKU
- 商品一致性检查可用
- 发布前能判断商品是否可售
- 已具备 Shoppable Video/Product Anchor 申请材料基础

## 5.7 V6：Shoppable Video / Product Anchor

### 阶段目标

在 Direct Post 和 TikTok Shop 商品能力成熟后，申请并接入 Shoppable Video / Product Anchor 能力，实现商品锚点自动化和成交复盘。

### 阶段本质

V6 不是“自动挂车爽点”，而是内容、商品、合规、发布、成交数据全部打通后的高阶能力。

V6 要解决的是：

```text
视频内容和商品是否一致？
商品锚点是否正确？
挂车是否成功？
用户点击和成交是否能回流？
哪些视频真正带来商品转化？
```

### 核心能力

| 能力 | 说明 |
|---|---|
| Shoppable Video 发布 | 发布带商品锚点的视频 |
| Product Anchor 配置 | 配置商品锚点标题、商品链接、商品 ID |
| 商品锚点预检查 | 预检查视频与 shoppable content anchor 是否违规 |
| 挂车状态追踪 | 记录商品锚点是否成功展示 |
| 点击/成交复盘 | 分析视频、商品、成交之间的关系 |
| 商品视频表现看板 | 看哪个 SKU、哪个视频、哪个账号带来效果 |

### 交付物

```text
Shoppable Video 接入
Product Anchor 配置
商品锚点预检查
挂车状态追踪
视频-商品-成交复盘
商品内容表现看板
```

### API 依赖

```text
TikTok Shop / Affiliate / Creator 相关高级权限
Shoppable Video / Product Anchor API
Precheck Video Content API，若权限可用
订单/成交/财务数据 API，若用于转化复盘
```

### 当前不做

V6 之前不做自动商品锚点。

V0-V5 只做：

```text
商品匹配建议
挂车操作指引
商品一致性检查
发布前商品校验
```

### V6 完成后的系统状态

V6 完成后，系统才真正形成完整闭环：

```text
商品池
  ↓
内容生产
  ↓
商品匹配
  ↓
合规审核
  ↓
授权发布
  ↓
商品锚点
  ↓
成交复盘
  ↓
下一轮内容优化
```

## 6. API 审核关系

### 6.1 API 能力地图

| API/能力 | 对应阶段 | 作用 | 产品证明 |
|---|---|---|---|
| TikTok Developer App | V2 | 注册应用、配置回调、准备审核 | 官网、隐私政策、服务条款 |
| OAuth / Login | V2 | 用户授权 TikTok 账号 | 授权中心、解绑、权限说明 |
| Content Posting Upload | V3 | 上传视频或提交发布任务 | 发布确认页、发布记录 |
| Direct Post / video.publish | V4 | 用户确认后公开视频发布 | 发布 UX、商业披露、发布日志 |
| TikTok Shop Product API | V5 | 商品、SKU、库存、价格同步 | 商品池、商品状态检查 |
| TikTok Shop Order/Finance API | V5/V6 | 成交、订单、财务复盘 | 数据复盘模块 |
| Shoppable Video / Product Anchor | V6 | 带商品锚点的视频发布 | 商品匹配、锚点预检查、挂车记录 |

### 6.2 产品设计如何服务 API 审核

| 产品设计 | 审核价值 |
|---|---|
| 授权中心 | 证明用户主动授权，不是后台盗用账号 |
| 账号解绑 | 证明用户有数据控制权 |
| 发布确认页 | 证明不是无人值守后台发布 |
| 视频预览 | 证明用户知道发什么 |
| 标题编辑 | 证明用户有最终内容控制权 |
| 隐私/互动设置 | 证明尊重 TikTok 发布体验 |
| 商业内容披露 | 证明重视电商内容合规 |
| 商品匹配 | 证明不是乱挂商品 |
| 合规检查 | 证明系统控制内容风险 |
| 发布日志 | 证明操作可追踪 |
| 数据删除说明 | 证明用户可撤销授权并删除数据 |

### 6.3 正式材料禁止表达

任何 API 申请材料、官网、产品介绍中，不允许出现：

```text
矩阵号
养号
批量群发
自动铺量
无人值守发布
自动绕过上传
模拟人工上传
规避风控
搬运视频
批量挂车卖货
```

应该使用：

```text
TikTok Shop 商家内容运营工作台
商家授权发布
商品匹配
合规审核
发布确认
发布记录
数据复盘
```

## 10. 当前版本结论

本项目必须按以下路线推进：

```text
V0 内部发布任务系统
  ↓
V1 商家内容工作台 MVP
  ↓
V2 TikTok OAuth 授权
  ↓
V3 Content Posting 测试
  ↓
V4 Direct Post 审核
  ↓
V5 TikTok Shop 商品能力
  ↓
V6 Shoppable Video / Product Anchor
```

当前不要继续幻想“一步到位自动发视频 + 自动挂车”。

正确做法是：

```text
先把商家内容运营流程做成系统；
再把系统做成 API 审核能理解的产品；
再逐步申请 TikTok 授权、发布、商品、商品锚点能力。
```

如果第一版直接做成“一键批量发 TikTok 视频”，这个项目会同时输在三个地方：

```text
产品上：不像商家内容运营工作台；
审核上：像高风险批量发布工具；
业务上：没有沉淀商品、内容、数据复盘能力。
```

所以本项目的主线必须是：

```text
内容运营工作台优先；
API 自动化后置；
商品锚点最后做；
浏览器自动化只作为实验分支。
```
